# ゲームプレイの時系列固定と探索の制限

更新日: 2026-10-17。設計提案とLean研究モデルであり、実行中のwire protocolや
MoonBit runtimeへ新しい乱数・ticketサービスを追加するものではない。
その後の[単独encounterの統合実装](./encounter-lifecycle-ja.md)では、
容量制限付き記録から署名付き乱数公開、実replay、市場受理、削除許可までを内部APIで接続した。

## 制限できる探索

クライアントへ渡した状態やプログラムは、コピーして別の入力で実行できる。
純粋なソフトウェアだけで任意の計算を一回限りにすることはできない。
[Goldwasser・Kalai・RothblumのOne-Time Programs](https://www.microsoft.com/en-us/research/publication/one-time-programs-2/)
もこの制約を述べ、専用のsecure memory deviceを使う構成を扱っている。

実用上は、受理される選択を一つに固定し、その後で初めて利用できる外部入力を与える。
これにより「結果を見てから行動ログを選び直す」「snapshotを戻して別の報酬を請求する」
攻撃を拒否できる。公開済み情報による探索や、botによる判断そのものの禁止は保証しない。
有効なゲームログを持つことは、人間が通常の操作方法で遊んだ証明にはならない。

| 狙い | 必要な仕組み | 残る限界 |
| --- | --- | --- |
| 報酬を知ってから戦闘ログを選び直せない | 戦闘rootの外部受理後に報酬seedを公開 | 公開済み戦闘条件での探索は残る |
| 将来の敵行動を先に計算できない | 未公開の次phase乱数、phase間のroot固定 | 現在のphase内の探索は残る |
| 過去の入力を後付けできない | 信頼できる時計で付けた受領証と締切 | 受領証のないクライアント時刻は根拠にならない |
| 同じ試行から複数の結果を換金できない | ticket/slotごとの単一ledgerと原子的な消費 | 台帳をコピー・巻き戻せる運用では保証できない |
| 試行の大量発行で良い乱数を選べない | 発行時点での予算消費、同時保有上限、固定seed、放棄時も再抽選しない | 無制限の複数accountを許す場合は別途対処が必要 |

## 提案する時系列

```text
確定済み開始状態と参加権を拘束してticket発行・予算消費
    ↓
直前に公開された条件でローカル実行
    ↓
入力集合・順序・件数と状態のrootを締切前にcommit
    ↓  authorityが単一台帳へ原子的に記録し、受領証を返す
予定時刻になったら、そのslotの未知だったseedを公開
    ↓
固定済みの行動を使って結果を解決／次phaseの条件を公開
    ↓
ゲーム実行の妥当性を別途検証し、ticketを一回だけ消費して資産受理
```

commit対象には少なくともticket ID、round、親receipt、開始state head、rules hash、
入力root・件数・順序、対象scopeを束縛する。署名付き受領証はcommit digestと
authorityの受領時刻・締切を束縛する。公開receiptも同じticket/round/commitへ結び付ける。
ここで固定する状態は、これから公開する乱数を適用する前の状態である。
公開後に決まる状態や報酬を先にcommitする必要はなく、公開された乱数と固定済み入力から検証する。
ゲーム側の妥当性を検証せずに、rootを預かっただけで報酬を確定してはいけない。

乱数は、例えば次の固定入力に対してauthorityの秘密鍵から生成する。

```text
r_i, proof_i = VRF_sk("game-challenge-v1", ticket_id, round_i)
```

[RFC 9381](https://www.rfc-editor.org/rfc/rfc9381.html)は、秘密鍵所有者が値を計算し、
公開鍵で正しさを検査できるVRFを定義する。同じ鍵と入力の出力は固定される。
ただしVRFだけでは「公開前に別経路で値を教えていない」ことや「締切前の入力受理」は証明できない。
鍵・ticket ID・roundを固定し、seedとproofを早期公開しないサービス側の責務が残る。
authorityがseedを事前に知ることも変わらない。authority自身の偏り・共謀も扱う場合は、
独立beaconやthreshold生成等の別の信頼モデルが必要になる。

同じslotへ別のrootを送っても拒否し、同じrootの再送は最初の受領証を返す。
切断後に再開する場合も同じticket・同じseedを使い、新しい抽選にはしない。
放棄や失敗で新しい無料ticketを得られると、よい結果になるまで再試行できるため、
発行時点の予算消費と再発行policyが重要になる。
通信失敗自体をcheatとは断定せず、再接続・保留として扱う。

未来の乱数を含む全seedを開始時にクライアントへ渡す方法では、先読みを防げない。
seedのhashだけを先に公開しても、seed自体を同時に渡せば同じ問題が残る。
クライアントだけが保存したcommitと自己申告時刻も、後から作り直せる。

## ゲームへの適用範囲

lootは相性がよい。戦闘結果・報酬資格を固定してからloot seedを公開すれば、
同じ試行について別の移動や攻撃ログを作ってdropを選び直す経路を閉じられる。
dropを見てからの放棄が無料再抽選にならないようにする。

敵行動はphase単位で扱う。phase `i`の入力を固定してから次の敵行動を公開すると、
その未知の敵行動まで使った未来の経路探索はできない。
ただし、敵の予兆を見て回避するゲームでは、予兆公開後に回避入力を選べる必要がある。
すべての行動を予兆公開前に固定する設計は、回避skillそのものを失わせる。
固定するのは過去の行動や、もともと事前選択する対象であり、通常移動はローカル予測を続ける。

5秒ごとに外部入力を更新しても、公開済み条件で現在の5秒区間を高速simulateする探索は残る。
サーバー上で最小経過時間を確認しても、待機してからログを高速生成するクライアントは識別できない。
より細かい受領・未知入力を必要とするほど通信頻度は増える。
完全offline、任意の再実行禁止、秘密を持つ信頼境界なし、という条件を同時には満たせない。

## VDFが担う範囲

[BonehほかのVDF](https://theory.stanford.edu/~dabo/abstracts/VDF.html)は、
指定された逐次計算を要し、結果を効率的に検査できる関数を扱う。
これは一回限りの実行や実際のゲーム操作の証明ではない。

- `VDF(ticket)`なら、結果を一度得た後は複数の行動分岐で同じ結果を再利用できる。
- `VDF(ticket, action_root)`なら、別候補ごとに計算費用を課せるが、複数候補を別の計算機で並行評価できる。
- 入力が事前に分かれば前計算が可能になるため、未知のchallengeとの束縛も必要になる。

必要な逐次計算数は、異なる端末で同じwall-clock時間になることも保証しない。
ゲームの進行をVDF計算待ちへ結び付けると端末負荷が増える。
今回の第一候補は、外部乱数の段階公開と不可逆なcommitを組み合わせる方式とする。

## 中央の費用と頻度

このサービスは、固定長rootの受領、単一slotのDB更新、乱数計算、receiptの署名を行う。
ゲームの物理演算や戦闘replayは別の検証経路へ置ける。
ただし通信回数までゼロになるわけではない。

2分encounterで境界ごとにcommitと次のchallenge取得を一往復にまとめる場合の算術例:

| 境界間隔 | 境界交換回数 / 2分 | 30 Hzの描画・入力frame数 |
| ---: | ---: | ---: |
| 5秒 | 24 | 3,600 |
| 1秒 | 120 | 3,600 |
| 0.25秒 | 480 | 3,600 |

開始・終了等の追加要求は含めない。receipt/VRFの処理時間は未計測であり、
既存の移転証拠benchmarkから、このサービスのlatencyを推定しない。
1万人が5秒ごとに送るなら平均2,000交換/秒になるため、固定長メッセージ、
scopeでの分割、burst制御やbatch化の検討は依然必要になる。
共通beaconの配布をまとめても、公開前に各commitが外部へ固定されていたという証拠は必要である。

commitをMerkle rootへbatch化する場合も、単なる候補の包含証明だけでは足りない。
同じ`(ticket, round)`について多数の候補を先に登録し、公開後に有利な候補のopeningを出す攻撃がある。
このkeyに対する値が一つだけであることを保証する台帳更新または検証済みmapが必要になる。
この一意性を省いて署名回数だけ減らす最適化は、今回の探索制限を保存しない。

## Leanの保証範囲

[`Chronology.lean`](../formal/lean/ConvergeAudit/Chronology.lean)では、1つの
authority発行ticket/slotについて、次の状態機械と16定理を追加した。

```text
fresh → locked → revealed → consumed
  └───────────────→ forfeited
```

`forfeited`へは`fresh`・`locked`・`revealed`から進め、`consumed`と`forfeited`には出口がない。
同じrootへのcommit再送だけが`locked`の自己遷移となる。

| 定理 | 保証 |
| --- | --- |
| `fresh_commit_iff` | 新規commitには締切前の受領が必要 |
| `retry_keeps_receipt`, `replacement_refused` | 再送は最初のroot・受領時刻を維持し、別rootを拒否する |
| `follows_preserves_pin`, `cannot_change_committed_root` | 任意長の成功履歴でも、固定済みrootは変わらない |
| `reachable_well_timed`, `reveal_after_commit`, `revealed_seed_fixed` | 到達状態の時系列と予定seedが整合する |
| `consumed_terminal`, `forfeited_terminal` | 請求・放棄後に同じslotは再利用できない |
| `redeem_cannot_repeat` | 1回の成功請求後、任意の後続履歴でも再請求できない |

28例で締切、早期公開、選択の差し替え、再請求、放棄、履歴合成を確認する。
台帳をコピーすると別rootをそれぞれ受理できる具体例も残した。
このモデルの`Follows`は同じ永続台帳の原子的な成功履歴であり、
署名・信頼できる時計・予測不能性・同時実行DBの実装・ticketの発行上限を証明していない。
seedはtrusted serviceの入力であり、クライアントへ先渡しするDTOではない。
gameplay妥当性、複数slotの親接続、報酬発行、探索確率の上限も別の証明義務となる。
